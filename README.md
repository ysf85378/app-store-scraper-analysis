## 接入方式与代码实操

ScraperAPI 的接入极其简单，本质就是在请求 URL 前加一层代理网关。以 Python 为例：

```python
import requests

API_KEY = "你的密钥"
target_url = "https://apps.apple.com/us/app/duolingo/id57060128"

response = requests.get(
    f"http://api.scraperapi.com?api_key={API_KEY}&url={target_url}&render=true&country_code=us"
)
```

`render=true` 是关键参数。App Store 页面大量依赖 JavaScript 动态加载，不开渲染拿到的是空壳 HTML。这个参数会消耗 10 个请求额度而非 1 个，选套餐时要把这个倍率算进去。

我的 47 个关键词追踪任务，实际消耗额度 = 1400 × 10 = 14000/天，月消耗约 42万。所以我选的是 Startup 套餐的年付方案，$99/月覆盖 50 万额度，刚好够用还有余量做临时抓取。

## 哪些场景不适合用 ScraperAPI

说实话，不是所有 App Store 数据需求都该走爬虫。

如果你只需要 App 的基本信息（名称、开发者、描述、评分、截图 URL），iTunes Search API 完全免费且稳定，没必要花钱。ScraperAPI 的价值在于拿那些官方 API 不给的数据：搜索排名位置、评论全文与时间线、分类排行榜实时变化、A/B 测试中的不同版本页面。

另外，如果你的需求是实时性极高的场景（比如秒级监控价格变化），ScraperAPI 的响应时间在 5-15 秒之间（含渲染），可能不够快。这种场景更适合 WebSocket 长连接方案。

## 提高成功率的三个细节

**第一，指定国家代码。** App Store 不同区的内容完全不同，不指定 `country_code` 参数会随机分配出口 IP 所在区域的结果，数据就乱了。

**第二，控制请求间隔。** 我设置了每次请求间隔 2-5 秒的随机延迟。虽然 ScraperAPI 内部有反检测机制，但从我的经验看，加上延迟后成功率从 94% 提升到 98%。

**第三，用 session 保持同一 IP。** 抓取分页评论时，如果每页换 IP，苹果可能返回重复数据或乱序。ScraperAPI 支持 `session_number` 参数，同一 session 内保持 IP 不变，分页数据就连贯了。

这三个细节是我第 2 个月才摸索出来的。前两个月成功率波动大，一度怀疑是 ScraperAPI 的问题，后来发现全是自己的请求策略不对。

## 常见问题直答

**Q：ScraperAPI 能绕过 App Store 的地区锁定吗？**
能。通过 `country_code` 参数指定任意国家的出口 IP，我同时监控美区、日区、港区、德区，从未遇到地区限制问题。

**Q：抓取频率有上限吗？**
官方没有硬性频率限制，但并发数受套餐约束。Startup 是 50 并发，意味着同时最多 50 个请求在跑。对 App Store 采集来说完全够用——并发太高反而容易触发目标站点的防护。

**Q：评论数据能拿到多久以前的？**
App Store 评论页支持按时间排序分页加载，理论上能拿到所有历史评论。实测中，超过 5000 条评论的 App 在翻到第 200 页左右会出现加载异常，这是苹果自身的限制，跟 ScraperAPI 无关。

**Q：请求失败会扣额度吗？**
不会。只有返回 200 状态码的成功请求才计入消耗。超时、403、5xx 都不扣。这一点比按流量计费的代理服务厚道很多。
